# Запрос на изменение № 1. Повторяющиеся задачи

| Поле | Содержание |
|---|---|
| Название | Повторяющиеся задачи |
| Автор запроса | Менеджер команды (заказчик) |
| Причина | В малой команде много регулярной работы: еженедельный отчёт, ежемесячная сверка, планёрка. Сейчас менеджер каждый раз создаёт такую задачу заново и иногда забывает, и задача снова «теряется» — та самая проблема, ради которой делается система. |
| Какие требования добавятся | **ФТ 19.** Менеджер должен иметь возможность задать для задачи правило повторения: ежедневно, еженедельно (с выбором дней недели) или ежемесячно (с выбором числа), с датой окончания или без неё. **ФТ 20.** Когда задача с правилом повторения переходит в статус «выполнена», система должна создать следующую копию задачи с тем же исполнителем, приоритетом и описанием и сроком по правилу. |
| Какие требования изменятся | ФТ 9: при удалении повторяющейся задачи менеджер выбирает «удалить только эту» или «удалить эту и все будущие». ФТ 16: исполнитель получает уведомление о созданной копии так же, как о новой задаче. |
| Что нужно изменить | **Архитектура:** модуль управления задачами (создание копий по правилу), модуль уведомлений (уведомление о копии). **Диаграмма классов:** новый класс RecurrenceRule (frequency, interval, daysOfWeek, dayOfMonth, endDate), связь Task 1 — 0..1 RecurrenceRule; у Task новый метод createNextOccurrence(). **Сценарии:** в сценарий 1 «Создание задачи» добавляется необязательный шаг «Менеджер задаёт повторение»; в сценарий 2 «Изменение статуса» — шаг «Система создаёт следующую копию». **Интерфейс:** поле «Повторять» в форме задачи, значок повторения в списке. **Тест-кейсы:** 3 новых. **Матрица трассировки:** 2 новые строки. |
| Новые тест-кейсы | ТК 13 — еженедельная задача: после статуса «выполнена» появляется копия со сроком через 7 дней и исполнитель получает уведомление. ТК 14 — правило с датой окончания: после последнего повторения копия не создаётся. ТК 15 — удаление «эта и все будущие»: копии больше не создаются, удаление записано в журнал действий. |
| Оценка трудоёмкости | 5 рабочих дней: модель и правило — 1, создание копий — 2, интерфейс — 1, тестирование — 1. |
| Новая версия | **1.2.0** — добавляется новая возможность, существующие функции продолжают работать как раньше. |
| Решение | Принять в бэклог со средним приоритетом; реализовать после итерации 2 (проекты и дашборд), так как правило повторения использует те же данные задачи. |

Одно новое требование затрагивает 6 документов: функциональные требования, архитектуру, диаграмму классов, оба сценария, тест-кейсы и матрицу трассировки. Поэтому изменение оформляется запросом и попадает в план, а не вносится в документы по ходу работы.
