Задание 4. Модель жизненного цикла и архитектура

**7. Модель жизненного цикла**

Для разработки системы управления задачами выбрана инкрементная модель. Причины такого выбора:

- Требования к системе будут уточняться по ходу проекта — как только команда начнёт пользоваться первой версией, появятся идеи, которых не было в исходном задании. Каскадная модель с её жёсткой последовательностью этапов здесь не подходит.

- Проект естественно разбивается на самостоятельные функциональные блоки. Каждая итерация заканчивается работоспособной версией системы — её можно сразу отдать пользователям.

- Это не критическая система (как банковское ПО или софт для медицинской техники), поэтому сложная спиральная модель с упором на минимизацию рисков избыточна.

- Размер команды и проекта позволяет обойтись без полного арсенала Agile (спринты, ежедневные митинги, скрам-мастер). Достаточно классических итераций с понятным составом работ.

Разбиение проекта на итерации:

| **Итерация** | **Что разрабатывается**                                                                                                                                     |
|--------------|-------------------------------------------------------------------------------------------------------------------------------------------------------------|
| **1**        | Базовое ядро: регистрация и авторизация, создание задачи, назначение исполнителя, просмотр списка своих задач, изменение статуса                            |
| **2**        | Командная работа: объединение задач в проекты, дашборд менеджера, комментарии и файлы к задачам, фильтрация и сортировка                                    |
| **3**        | Автоматизация: уведомления о новых задачах и изменениях, история изменений, синхронизация при временной потере соединения                                   |
| **4**        | Администрирование и аналитика: управление учётными записями и ролями, отчёты по выполненным и просроченным задачам, журнал действий, многоязычный интерфейс |

После первой итерации команда уже получит работоспособную версию для базовых сценариев — создания задач, их распределения и отслеживания статуса. Следующие итерации дополнят её, не ломая того, что уже работает.

**8. Архитектура системы**

Система построена по клиент-серверной архитектуре. Клиентская часть — это веб-интерфейс и мобильное приложение, через которые пользователи работают с задачами. Серверная часть разбита на функциональные модули и обслуживает запросы клиентов через единый API-шлюз. Все данные хранятся в общей базе данных.

Состав модулей:

| **Модуль**                             | **Назначение**                                                                                                                      | **С чем взаимодействует**                                      |
|----------------------------------------|-------------------------------------------------------------------------------------------------------------------------------------|----------------------------------------------------------------|
| **Модуль интерфейса**                  | Отображает задачи, формы и дашборд; принимает действия пользователя в браузере или мобильном приложении.                            | Модуль авторизации, API-шлюз серверной части.                  |
| **Модуль авторизации и пользователей** | Регистрация, вход по логину и паролю, управление учётными записями, назначение ролей (исполнитель, менеджер, администратор).        | Интерфейс, база данных, модуль журнала действий.               |
| **Модуль управления задачами**         | Создание, редактирование, удаление задач и проектов, смена статусов, назначение исполнителей, прикрепление файлов и комментариев.   | Интерфейс, база данных, модуль уведомлений, модуль отчётности. |
| **Модуль уведомлений**                 | Формирует и отправляет уведомления о новых задачах, изменениях статуса и приближении срока — внутри системы и по электронной почте. | Модуль управления задачами, база данных.                       |
| **Модуль отчётности и аналитики**      | Собирает данные для дашборда менеджера, формирует отчёты по выполненным и просроченным задачам за выбранный период.                 | Модуль управления задачами, база данных.                       |
| **База данных**                        | Хранит пользователей, задачи, проекты, комментарии, файлы и историю изменений; обеспечивает резервное копирование.                  | Все серверные модули.                                          |

Такое разбиение покрывает все функциональные требования из задания 2: авторизация и роли — через модуль пользователей, работа с задачами — через модуль управления задачами, автоматические уведомления и история изменений — через соответствующие модули, отчёты для менеджера — через модуль отчётности.
